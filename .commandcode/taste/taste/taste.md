# Taste
- When doing frontend/UI work, inspect the actual backend contract before wiring UI; use it as-is (never invent endpoints, routes, or response fields); make only the necessary frontend changes; keep current design and functionality intact; preserve unrelated existing actions, pages, and routes; do not modify backend code or add dependencies; keep form values dynamic and avoid prefilled example subjects/titles that could be mistaken for real data; preserve existing authentication and API configuration; and document any required backend changes concisely in backend_services.md (append entries, preserve existing history, don't rewrite the file). Also: never simulate missing persistence with frontend-only dummy/mock data ("dummy saved configurations", fake samples) — if the backend lacks an endpoint, report the required contract instead and keep any client-side fallback behind a single swappable seam. The user reiterates these rules explicitly in every task brief. Confidence: 0.95
- For API/feature errors, surface the actual backend error message to the user instead of a generic or misleading fallback (while still using generic messages for auth/security failures like 401/429 so secrets are not leaked). Confidence: 0.75
- For login and form flows, the keyboard must be first-class: Enter should submit, fields should auto-focus (first empty field on page load / when revealed), and nothing (e.g. hidden `required` inputs) should silently block native submission. Confidence: 0.7
- Always serve/demo/test the Smart QPG UI at http://localhost:3000 — the backend's CORS default allows this origin; never use other ports like 5500/5173 for the UI. Confidence: 0.95
- When completing code changes, report the files changed and the checks actually performed. Confidence: 0.7
- For API-driven UI sections, always implement proper loading, empty, error, and retry states (e.g., a retry button on failure) rather than a static placeholder; a single missing file or failed request must not break the entire page. Confidence: 0.8
- Job polling should run only while a job is active (roughly every 4–5s), stop on success/failure or when leaving the processing screen, deduplicate timers and prevent overlapping requests, allow manual status refresh, and render progress/errors from the backend's actual job response; never poll inactive or completed jobs continuously. Confidence: 0.8
- Prevent stale API responses and duplicate fetching by gating renders with a request token and deduping in-flight loads (e.g., a shared, cached `ensure…Loaded()` promise so selecting/refreshing the same resource does not refire or overwrite with stale data). Confidence: 0.75
