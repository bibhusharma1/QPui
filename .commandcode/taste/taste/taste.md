# Taste
- When doing frontend/UI work, inspect the actual root files/modules and API configuration before changes and the actual backend contract before wiring UI; use it as-is (never invent endpoints, routes, or response fields, and never assume file paths or introduce a parallel implementation); make only the necessary frontend changes; keep current design and functionality intact; preserve existing UI design and API architecture; preserve unrelated existing actions, pages, and routes; do not modify backend code or add dependencies unless backend validation is genuinely necessary; keep frontend validation consistent with backend generation validation; keep form values dynamic and avoid prefilled example subjects/titles that could be mistaken for real data; preserve existing authentication and API configuration; never use localStorage as a substitute for backend job/document state; and document any required backend changes concisely in backend_services.md (append entries, preserve existing history, don't rewrite the file). Also: never simulate missing persistence with frontend-only dummy/mock data ("dummy saved configurations", fake samples) — if the backend lacks an endpoint, report the required contract instead and keep any client-side fallback behind a single swappable seam. When fixing calculation/UI bugs, fix the underlying calculation and state-management logic rather than merely changing displayed numbers. The user reiterates these rules explicitly in every task brief. Confidence: 0.95
- For API/feature errors, surface the actual backend error message to the user instead of a generic or misleading fallback, and never hide errors (while still using generic messages for auth/security failures like 401/429 so secrets are not leaked). Confidence: 0.75
- For login and form flows, the keyboard must be first-class: Enter should submit, fields should auto-focus (first empty field on page load / when revealed), and nothing (e.g. hidden `required` inputs) should silently block native submission. Confidence: 0.7
- Always serve/demo/test the Smart QPG UI at http://localhost:3000 — the backend's CORS default allows this origin; never use other ports like 5500/5173 for the UI. Confidence: 0.95
- When completing code changes, report the root cause, the exact files changed, and the checks actually performed. Confidence: 0.75
- For API-driven UI sections, always implement proper loading, empty, error, and retry states (e.g., a retry button on failure) rather than a static placeholder; loading states must always terminate on success, failure, timeout, or network error with no stale indicators or duplicate notifications; distinguish document-not-found (404), authentication, server, and network failures; a single missing file or failed request must not break the entire page. Confidence: 0.8
- Job polling should capture the job ID returned on acceptance (e.g. 202) and poll the corresponding `/jobs/{job_id}` endpoint until a terminal state; handle `queued`, `processing`, `completed`, and `failed` from the actual backend response; keep exactly one active polling loop per job ID even when multiple components or refresh handlers request it; stop immediately on completed/failed/other terminal states; clear timers/timeouts and guard against overlapping in-flight requests; never restart polling for a completed job on list refresh or page revisit; use adaptive backoff intervals instead of frequent fixed-interval requests; clean up obsolete pollers on navigation and resume only an already-running job if the user returns; run only while a job is active, stop on success/failure or when leaving the processing screen, clear loading indicators on failure, and display the backend's actual useful error; deduplicate timers and prevent overlapping/duplicate processing requests, allow manual status refresh, refresh the correct subject's list on completion/failure, and render progress/errors from the backend's actual job response; never poll inactive or completed jobs. Confidence: 0.9
- Prevent stale API responses and duplicate fetching by gating renders with a request token and deduping in-flight loads (e.g., a shared, cached `ensure…Loaded()` promise so selecting/refreshing the same resource does not refire or overwrite with stale data); refresh list state after upload, processing completion/failure, removal, and subject changes while preserving the selected subject and filters; key Process/Result/Review/Remove/DOCX actions to the document's own persisted subject and filename as source of truth rather than the currently selected filter. Confidence: 0.75
- Never prompt users to enter IDs (e.g., blueprint IDs); IDs are generated by the backend, and if the backend contract instead requires a client-supplied ID, document that required backend change in backend_services.md rather than working around it with client-fabricated IDs. Confidence: 0.85
- For generated examination papers/DOCX output, use a formal academic layout: black text (#000000), formal fonts (preferably Times New Roman), consistent font sizes and paragraph spacing, proper alignment of question numbers and marks, clear section headings, consistent page margins and page breaks, and no decorative colours, gradients, emojis, or informal styling. Student-facing papers must also exclude internal processing notices, OCR warnings, parser diagnostics, and internal source metadata; keep source references separate for administrative review if the system supports them. Confidence: 0.9
- Do not show confirmation dialogs/prompts before retry or reprocess actions; execute them immediately on user click. Confidence: 0.85
- For PYQ PDF processing, label successfully processed PDFs as "Parsed" (not "Completed") and keep their existing results available without re-triggering processing. Confidence: 0.8
